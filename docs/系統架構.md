# 系統架構與分析

本文說明這個系統怎麼組成、資料怎麼流動、以及每個設計決策背後的理由。
欄位層級的說明在 [`欄位說明.html`](欄位說明.html)。

狀態快照：2026-10-06。資料庫 143 MB / 512 MB，54 個篩選欄位。
**歷史回補已於 2026-10-05 全部完成**（五個資料集各 3,083 / 3,083）。

## 二、資料流

### 每日同步（`scripts/sync.ts`）

一次交易日收盤後跑，**9 次 API 呼叫涵蓋全市場**：

| 來源 | 寫入 | 筆數 |
|---|---|---|
| FinMind `TaiwanStockInfo` | `stock` | 3,081 |
| 證交所／櫃買 公司基本資料 ×3 | `stock_capital` | 2,351 |
| 證交所／櫃買／興櫃 行情 ×3 | `stock_daily` | 2,754 |
| 證交所／櫃買 本益比 ×2 | `stock_daily`（同上，合併） | — |
| 證交所／櫃買 董監持股 ×2 | `stock_insider` | 1,975 |
| 證交所／櫃買 月營收 ×2 | `stock_revenue` | 1,978 |

整批包在一個交易裡。乾跑模式會把所有 INSERT 真的跑完、驗證型別與外鍵、
回報實際落地筆數，然後 rollback——不是「只印不做」。

### 歷史回補（`scripts/backfill.ts`）

FinMind 逐檔，四個資料集依序處理，進度記在 `backfill_log`：

| 順序 | 資料集 | 每檔呼叫 | 一次拿到 | 產出 |
|---|---|---|---|---|
| 1 | `dividend` | 1 | 十年配息 | `stock_dividend` |
| 2 | `annual` | 2 | 十二年日頻＋評價 | `stock_annual`、`stock_daily` |
| 3 | `quarterly` | 2 | 46 期損益＋資產負債 | `stock_quarterly` |
| 4 | `revenue` | 1 | 141 個月營收 | `stock_revenue` |
| 5 | `cashflow` | 1 | 46 期現金流量 | `stock_quarterly` 的 `cf_*` 欄位 |
| 6 | `parquet` | 1 | 十二年日頻 | 年度 Parquet（冷資料） |

一輪之內會把時間用完才停：目前這個資料集清空了就接下一個。
原本是「挑第一個沒補完的跑完就結束」，結果主檔多兩檔新股票就讓配息變回
「沒補完」，整輪花十幾秒補那兩檔就收工——一個六小時的窗只做了十幾秒的事。

## 三、模組職責

| 檔案 | 負責 | 不負責 |
|---|---|---|
| `lib/twse.ts` | 證交所／櫃買 open API 的取得與正規化 | 資料庫 |
| `lib/finmind.ts` | FinMind API、限流退避 | 資料庫 |
| `lib/mops.ts` | 證交所季報（**已停用**，見決策 4） | — |
| `lib/live.ts` | MIS 即時報價 | 資料庫（刻意不寫入） |
| `lib/history.ts` | 線圖的日線與技術指標 | 資料庫（刻意不寫入） |
| `lib/http.ts` | 帶重試的 fetch、併發限制 | 業務邏輯 |
| `lib/parquet.ts` | DuckDB 產生 Parquet | 上傳（由 workflow 負責） |
| `lib/prisma.ts` | 連線（延遲初始化） | 查詢 |
| `lib/screener.ts` | 條件解析、SQL 組裝、衍生計算 | 畫面 |
| `lib/saved-filter.ts` | 條件儲存器（server actions） | — |
| `scripts/sync.ts` | 全市場增量 | 逐檔 |
| `scripts/backfill.ts` | 逐檔歷史、節流、進度 | 全市場 |

client component 有三個：`AppNav.tsx`（頂部導覽）、`StockPicker.tsx`（多選器）、
`StockChart.tsx`（K 線圖）。
其餘都是 server component，篩選條件靠一般的 GET form 送出，所以條件天然留在網址上。
線圖的期間切換也走網址（`?range=6m`），所以「台積電近半年」這種畫面可以直接分享。

### 手機版面

三個頁面都是同一組資料密集的表格，手機上真正會壞掉的只有兩件事，
其餘靠 Tailwind 的斷點就夠了：

**橫捲時沒有錨點。**篩選器有 73 欄、寬 5,800px，手機一定要橫捲。
捲到中間若不知道在看哪一檔，整排數字就失去意義。
所以把「股號」「股名」兩欄 `position: sticky` 釘在左邊。
釘住的儲存格要自己帶背景色（不然底下內容會透出來），
而且要跟著整列的 hover 變色，否則滑過時只有那兩格沒變、看起來像壞掉。

**條件區會把結果推出螢幕。**三十幾個欄位在手機上要捲十個螢幕才看得到結果。
用 `checkbox + peer` 做純 CSS 的收合（`hidden peer-checked:grid lg:grid`），
手機預設收起、桌機永遠展開。用 CSS 而不是 client component，
就沒有「伺服器算一套、瀏覽器算另一套」的水合不一致問題。
收起來時標題會標出已設定的條件數，不然看不出自己篩了什麼。

其餘：觸控目標在手機加大到 40px 以上（`py-2.5 sm:py-1.5`）、
線圖高度 `h-[300px] sm:h-[460px]`、多選器限高可捲
（50 個 chip 會佔滿整個螢幕）、操作提示依裝置切換文案。
viewport 刻意不鎖縮放——有寬表格的頁面，使用者一定會想放大看某幾欄。

> 驗證時繞了一段冤枉路：headless Chrome 的視窗有**最小寬度約 492px**，
> 下 `--window-size=390` 它會在 492 排版、只截左邊 390，看起來像整頁溢出。
> 量過 `html.scrollWidth === clientWidth` 才確認版面本來就沒問題。
> 要截真正的 390，得用 `--window-size=492 --force-device-scale-factor=1.2615`。

### 導覽：全站固定，而不是各頁各自的返回連結

原本每頁自己放一行「← 回篩選器」。問題是位置每頁不一樣，使用者要先找
「返回在哪」；而且純文字連結夾在一堆資料裡辨識度很低，常被當成說明文字。

改成固定在最上方的導覽列（`AppNav.tsx`），解決三件事：
位置永遠一致不用找、用底色標出目前在哪一頁、可以直接跳到任一頁而不只是上一頁。

個股頁多一顆「← 返回」按鈕——它是從篩選器或即時報價點進來的，
回到「剛才那一頁」比回到首頁更符合當下的意圖。
直接開連結進來（`document.referrer` 不是本站）時退回首頁，不會跳出站外。

### 即時報價的預設清單

一進來給**市值前 50 大的上市股票**，用「收盤價 × 已發行股數」現算而不寫死——
成分每年都會變，寫死的清單過一陣子會混進已經不是權值股的公司。
只取股號四碼純數字的上市股票，這一刀同時濾掉 ETF（00 開頭）與特別股（2881A）。

但只要網址上出現過 `ids` 或 `q`（哪怕是空字串），就完全尊重使用者的選擇、
不再塞預設——把自己的清單清空時，不該又跳出 50 檔要他再刪一次。

### 日線／週線／月線：先聚合再算指標

週 K 是把同一週的日 K 合起來：開盤取該期第一天、收盤取最後一天、
最高最低取區間極值、量與金額加總。代表日期用**該期最後一個交易日**，
這樣最後一根（還沒走完的那一週）的日期就是「資料到哪一天」。

關鍵是順序：**先聚合，再在聚合後的 K 棒上算指標**。
反過來做（算完日線指標再抽樣）得到的是「20 日均線畫在週圖上」，
那不是週線的 MA20。實測台積電：

| | MA20 |
|---|---|
| 日線 | 2,466.25 |
| 週線 | 2,407.00（＝20 週均，手算相符）|

兩者本來就該不同。圖例也會跟著標成 `MA20(週)`、`市場成本20週`，
不標的話看週線會以為還是日均線。

法人買賣超是**流量**，聚合時加總；外資持股比率與融資餘額是**時點**，
取該期最後一個有值的——加總會得到沒有意義的數字（持股比率變成 300%）。

週的分組用 ISO 週（週一起算）。跨年那一週不能直接用「年份＋週數」硬拼，
12/31 可能屬於隔年第 1 週，所以先把日期移到該週的週四再取年份。

期間的預設隨週期調整：日線近 1 年、週線近 3 年、月線全部——
週線看 3 個月只有 13 根，太稀疏。

### 線圖的資料為什麼不走資料庫

`stock_daily` 只有收盤價，沒有開高低——畫不出 K 線。完整 OHLC 在 Parquet 與 FinMind。

成本不在「欄位」而在「保留期間」。加三個 OHLC 欄位到現有的 459,847 列只要
**約 12 MB**，很便宜；但 `stock_daily` 為了省容量只留「月底 120 期 ＋ 近 61 個
交易日」，所以畫出來的 K 線**只有最近三個月是連續的**，再往前只剩月底的孤點。
要連續一年就得把保留期間拉到 250 天，那是 **+57 萬列、約 +110 MB**，
會把 2.9 年的容量餘裕吃掉大半。

而且看線圖本來就是「一次看一檔」——為了偶爾看的那幾檔，去存 3,007 檔的逐日
OHLC，比例完全不對。實測 FinMind 一次呼叫 **276~414 ms** 就拿到十年 2,865 列，
這個延遲在畫面上感覺不出來。

所以線圖跟即時報價採同一個原則：**不落地，要的時候才去拿**，加一層五分鐘的
行程內快取（切換期間時不該重打 API）。

### 籌碼面：拿不到的就說拿不到

「籌碼集中度」最想要的是**分點買賣超**（前 15 大券商），但 FinMind 免費層
直接擋住：`TaiwanStockTradingDailyReport` 與 `TaiwanStockHoldingSharesPer`
都回 HTTP 400（`Your level is register`）。那是付費功能，不是額度問題。

改用兩個免費的替代，實測單檔十年各 2,864 列、約 1.1 MB、130~506 ms：

| 資料集 | 內容 | 代表 |
|---|---|---|
| `TaiwanStockShareholding` | 外資及陸資持股比率 | 法人籌碼的長期趨勢 |
| `TaiwanStockMarginPurchaseShortSale` | 融資融券餘額 | 散戶籌碼 |

這組其實比分點更適合看趨勢——分點只看得到當天，持股比率看得到十年。
實測台積電 2015 年 77.32% → 2026 年 69.20%，同期融資餘額從 20,527 張
升到 30,135 張：**外資降、融資升，籌碼從法人流向散戶**。

這兩支各要一次呼叫，所以**刻意不放在預設路徑上**——只有切到籌碼副圖
（走網址 `?pane=chips`）時才抓。預設瀏覽維持 2 次呼叫，
不為了選用的功能在每次瀏覽都付固定成本。副圖選擇器因此是不對稱的：
從 K 線現算的那幾個是純前端切換，籌碼那一個是連結。

### FinMind 額度：背景工作讓給前台

register 層是 600 次/小時。回補原本設 560，只剩 40 給別人——
線圖每開一檔要打 2 次（日線 ＋ 法人），很容易撞到上限。

改成回補用 **480**、保留 **120/hr** 給互動式用途。
回補慢 17%（背景工作，沒人會感覺到），線圖則不會再因為背景工作而載不出來。
這是刻意的取捨：**背景工作不該把前台的額度吃光**。

## 四、資料模型

```
stock ──┬── stock_daily      (stock_id, trade_date)   日頻行情與評價
        ├── stock_quarterly  (stock_id, period_end)   季頻財報，存單季
        ├── stock_dividend   (stock_id, ex_date)      逐筆除息
        ├── stock_annual     (stock_id, year)         年度彙總
        ├── stock_capital    (stock_id, report_date)  股本與股數
        ├── stock_insider    (stock_id, period_end)   內部人持股
        └── stock_revenue    (stock_id, month)        月營收

saved_filter  (id)                     存起來的篩選條件
backfill_log  (stock_id, dataset)      回補進度，刻意不設外鍵
```

### 對位規則不是統一的，各有理由

| 表 | 規則 | 為什麼 |
|---|---|---|
| `stock_quarterly` | 嚴格 `period_end <= trade_date` | 用交易日之後才公告的財報去篩，是看未來資料 |
| 均線 MA5/10/20 | 往前 20 筆，而且要落在 40 個日曆天內 | `stock_daily` 只留月底＋近 61 日。歷史基準日取到的是「20 個月底」，算出來的「20 日均線」其實是 20 個月均價——數字正常、意義不同。實測 2025-06-30 橫跨 578 天，守門擋掉 |
| 股本 | 優先 `stock_quarterly.capital_stock`，缺才退回 `stock_capital` | 公司基本資料只有最新一兩期，切到歷史日期會拿到今天的股本。實測鴻海 2016 年 1,733 億、2019 年 1,386 億（2018 減資），差兩成 |
| 年度 EPS | 只採四季齊全的年度 | 少一季會把該年低估，而低估的那年會假裝成「衰退」，把連續成長紀錄硬生生切斷 |
| `stock_insider` | 嚴格 `period_end <= trade_date` | 同上 |
| `stock_capital` | 優先 `<=`，沒有才取之後最接近 | 公司基本資料的出表日常比交易日晚（2026-09-28 出表對應 2026-09-24 行情），只寫 `<=` 的話最新一天完全對不到 |
| `stock_annual` | 完整年度，`year <= 基準年 - 1` | 把只過了一半的當年混進平均，下半年配息的公司會被嚴重低估 |
| `stock_dividend` | 以基準日往回推 12 個月 / N 年 | 滾動窗口 |

## 五、關鍵設計決策

### 決策 1：時間是鍵，不是欄位名

原始需求是一份欄位清單，長這樣：

```
20180124 殖利率(交易所公告)近1日
2012~2016 現金股利殖利率(%)5年
201703 毛利率(%)(累計)
```

**122 個欄位，但其實只有約 50 個不同的資料項**，其餘是同一項在不同時間點的重複。
把日期寫進欄位名的話，換一個基準日就要改表結構。

改成日期存 `trade_date`、查詢時當參數傳，滾動彙總用視窗函數現算。
換基準日只是換一個參數。

### 決策 2：存最細的粒度，粗的現算

財報存**單季**，累計、近四季與**年度**都查詢時加總。

理由是單向性：
```
累計   = 同年度各季加總     ✓ 算得出來
近四季 = 最近四季加總       ✓ 算得出來
年度   = 該年四季加總       ✓ 算得出來
單季   = 累計相減           ✗ 缺任何一期就算不出來
```

證交所給累計、FinMind 給單季，實測可精確互換——台積電 2026
Q1 1,134,103,440,000 ＋ Q2 1,270,380,250,000 ＝ 2,404,483,690,000，
與證交所公告的上半年累計一字不差，EPS 22.08 ＋ 27.25 ＝ 49.33 也相同。

### 決策 3：冷熱分層

十年逐日全放進資料庫要 690 萬列、超過 1 GB，撞爆免費層。

```
熱（資料庫）   每月最後交易日 120 期 ＋ 最近 61 個交易日   實測 81 MB
冷（Parquet）  完整十年逐日，一年一檔共 12 個             實測 93.9 MB
```

實測一檔十二年 2,860 列：JSON 364 KB → Parquet(ZSTD) 39–59 KB。
Parquet 放 GitHub Release，不計入 repo 大小、單檔上限 2 GB，
DuckDB 可以直接查網址不用下載整包。

**分檔方式改過一次。**原本一檔股票一個檔，檔名就是股號，重跑靠 `--clobber`
覆蓋同名 asset 天然去重。但 **GitHub 每個 release 最多 1,000 個 asset**，
3,081 檔放不下——補到第 1,000 個（`3567.parquet`）就被擋，之後每輪上傳都失敗。
改成一年一個檔共 12 個，順便解掉「查某一天的全市場要開 3,081 個檔」。
代價是不能再一檔寫完就上傳：逐檔先累積成每年一個 NDJSON，整輪結束才跟
既有年度檔合併輸出，合併時用 `stock_id` 比對把重抓過的那些列整批換掉。

**否決的替代**：Cloudflare R2。免費額度更好（10 GB、流量免費），
但即使用免費額度也要先綁信用卡。GitHub Release 不用另開帳號，
而且檔名用股號 ＋ `--clobber` 上傳，重跑天然覆蓋不會累積重複——
R2 方案原本要按批次命名，重跑會產生重疊。

### 決策 4：季報只用 FinMind，停用證交所那份

兩個來源口徑不同（累計 vs 單季），寫進同一張表會變成一半累計一半單季，
**而且從欄位看不出來是哪一種**。加上證交所那份在金控與保險有欄位錯位（見第六節）。

所以讓 FinMind 當唯一來源，`lib/mops.ts` 保留但不再被呼叫。
順帶省下每天 24 次 API 呼叫。

### 決策 5：篩選條件放在網址，不存結果

存結果隔天股價一變就不準；條件永遠可以重跑。
儲存器存的內容就是網址的 query string，跟把網址分享給別人是同一份東西。

要留當下快照就下載 CSV。

### 決策 6：缺值是 null 不是 0

本益比 0 的意思是「沒有意義」不是「最便宜」。不濾掉的話
「近 N 年最低本益比」會全部變成 0，而那一欄正是便宜價的輸入。

同樣的原則套用在：營收為零時不算利潤率、去年同期為零或負時不算成長率、
權益為零時不算 ROE。

### 決策 7：預估 EPS 自己算

法人預估沒有免費來源——實測 CMoney、鉅亨、Yahoo、玩股網的公開頁面都沒有
（CMoney 個股 18 種頁面全掃，「預估」「EPS」出現 0 次）。

改用月營收推估。相對法人估有兩個優勢：**算式公開可檢驗**，
而且**月營收有十年歷史所以可回測**——法人估拿不到歷史預估值，反而驗不了準不準。

## 六、上游資料陷阱

這一節是實測累積出來的。每一條都曾經產生過看起來像數字、實際上錯的結果。

| 陷阱 | 現象 | 處理 |
|---|---|---|
| **證交所金控業損益表欄位錯位** | 「淨收益」對不上利息淨收益＋利息以外淨收益；13 家全部「稅前淨利 < 稅後淨利」，會計上不可能 | 停用證交所季報，改 FinMind（其淨收益 106,275,016,000 ＝ 56,958,729,000＋49,316,287,000，自洽） |
| **證交所保險業營收與營益不可信** | 旺旺保營益 1,931,456 > 營收 930,279；中再保營益是營收 6 倍 | 同上 |
| **內部人持股一人多列，每列都記全額** | 中華電的交通部掛董事長＋七席董事＋大股東共九列，每列 2,737,718,976 股，直接加總持股比例變成 **317.64%** | 寫入前依姓名去重，去重後 35.29%，符合交通部實際持股 |
| **FinMind 型別名稱各行業不同** | 金控與銀行是 `IncomeAfterTax`（少一個 s）、銀行稅前是 `IncomeBeforeTaxFromContinuingOperations`、證券營收是 `Income` | 每個欄位用別名清單依序試 |
| **同一個 type 在兩支 API 意義不同** | `EquityAttributableToOwnersOfParent` 在損益表是「淨利歸屬母公司」、在資產負債表是「母公司權益」 | 兩張對照表分開，不共用 |
| **現金流量是累計，損益表是單季** | 同一個 FinMind、同一家公司，兩支 API 的口徑相反。實測台積電 2025 四期的期初現金餘額全部相同（都是年初的 21,276 億），營業活動 6,256 → 11,226 → 15,495 → 22,750 單調遞增 | 寫入前相減轉成單季。驗證：6,256＋4,970＋4,269＋7,255 ＝ 22,750 億，與 Q4 累計完全相同 |
| **金融業沒有資本支出** | 金控／銀行的現金流量表沒有「取得不動產、廠房及設備」這一項 | 上游就沒有，留 null。自由現金流等於營業現金流 |
| **金融業沒有 EPS** | FinMind 的金控／銀行／證券／保險損益表完全沒有 EPS | 上游就沒有，不是漏抓；留空 |
| **GitHub Release 的 1,000 個 asset 上限** | 一檔股票一個 Parquet，補到第 1,000 個（`3567.parquet`）就被擋，之後每輪上傳都失敗。回補本身是好的，只有 job 紅燈——實際踩到兩次（run #6、#8） | 改成一年一個檔，12 個遠低於上限。run #9 起恢復綠燈 |
| **上游重複列** | 00878 的 2023-08-16 出現兩次，金額與發放日相同，只有 `date` 不同 | 去重不能加總——加總會讓那次配息變兩倍、殖利率虛增一倍 |
| **本益比 0 不是最便宜** | 虧損或無資料時上游給 0 或 null | 非正數一律視為無意義濾除 |
| **某個市場的行情回空，但 job 還是綠燈** | 2026-09-30 的同步：上櫃 1,013 筆、興櫃 362 筆都寫了，只有上市回空陣列。那天上市只剩 329 檔（歷史回補順手寫的），低於基準日門檻，**整天從下拉選單消失** | 有市場回空但其他市場有資料就直接丟錯不寫入；三個同時回空才當休市日 |
| **ETF 沒有財報也不公告月營收** | 3,083 檔裡 395 檔是 ETF，季報回補回傳 0 列。股號 `00` 開頭排在最前面，所以回補一開始會連續幾百檔都是 0 | 不是失敗，照常記進度；但容量估算要扣掉 |
| **三個市場 API 更新時間不一致** | 14:40 跑同步時興櫃已更新到 09-29、上市上櫃還停在 09-24，資料庫出現只有興櫃 360 筆的日期 | 基準日只列「有上市資料、有本益比、檔數達最佳日期四分之一」的日子 |
| **冷門股的「最近 61 個交易日」跨很長** | 那是它自己的最後 61 個有成交日，可能跨數年，生出 1,075 個不到 10 檔的日期 | 同上的覆蓋度門檻 |
| **股本合計含特別股** | 每股淨值分母用普通股股本會偏高（富邦金 90.50 vs 官方 81.22） | 優先用股本合計對齊官方口徑；上游缺的情況已記錄在欄位說明 |

### 非資料面的陷阱

| 陷阱 | 現象 |
|---|---|
| **PowerShell 吃掉前導零** | 未加引號時 `--stocks=2330,0056` 被當成陣列、`0056` 轉成數字，實際傳入 `2330,56,878`。不報錯，只是安靜查錯股票，而台股 ETF 代號全靠前導零 |
| **`Number(null)` 是 0 不是 NaN** | 害統一證每股淨值算成 0.00 |
| **重試包不到 response body** | `fetch()` 在 headers 到達就 resolve，body 傳到一半斷線會在 `res.json()` 才丟 `ECONNRESET`，只包 `fetch()` 的重試攔不到 |
| **`bash -e` 不含 `pipefail`** | 接了 `tee` 之後同步失敗會被 `tee` 的 exit 0 蓋掉，job 顯示綠燈但資料沒寫進去 |
| **GitHub 排程不可靠** | 設定完全正確但每小時 `:30` 連續三小時一次都沒觸發。官方明說是盡力而為，整點半點最壅塞 |
| **GITHUB_TOKEN 不能觸發 workflow** | 用內建 token 觸發的事件不會產生新的 workflow run，所以自我串接跑不起來 |

## 七、執行時序

```
每日 18:00 台北（10:00 UTC）    sync.yml
  ├ 來源連通性檢查（7 個端點的 HTTP 狀態 ＋ runner 對外 IP）
  ├ secret 檢查（只印長度不印值）
  ├ 空市場守門（有市場回空但其他有資料 → 直接失敗，不寫入）
  ├ 同步（9 次呼叫，整批一個交易）
  └ 結果貼到 job summary

> 實測這個排程也會遲到：設 10:00 UTC，實際兩天都在 16:2x UTC 才跑。
> 不影響正確性（上游給的是最近一個交易日），但要有心理準備。

每 6 小時 :07                   backfill.yml
  ├ 依序走完五個資料集，目前這個清空了就接下一個
  ├ 逐檔處理 4.7 小時（節流 560 次/小時），時間到就停
  ├ parquet 資料集收尾時把 NDJSON 合併成 12 個年度檔
  └ 上傳到 daily-parquet-year release（--clobber）
```

排程為什麼是 6 小時而不是每小時：實測每小時觸發根本不可靠。
改成單輪跑滿、觸發次數少一個數量級，錯過一次的代價也小得多。
job 逾時設 5 小時、腳本自己抓 4.7 小時，確保前一輪一定先結束——
兩輪重疊的話 FinMind 的呼叫速率會加倍而撞額度。

## 九、故障模式

| 狀況 | 表現 | 處理 |
|---|---|---|
| Neon 休眠 | 第一次開頁面多等幾秒 | 免費層特性，重新整理就快 |
| FinMind 額度用盡 | 402 / 429 | `http.ts` 退避重試，`backfill_log` 不記進度所以下次會重做 |
| 上游端點改版 | 解析後欄位全空 | 目前沒有自動偵測，靠畫面整欄空白發現 |
| 單一市場暫時回空 | 那天少一整個市場，基準日下拉會少一天 | 同步直接失敗不寫入，下一輪重跑 |
| 回補中途失敗 | 該檔不記進度 | 下一輪自動重試 |
| 排程沒觸發 | 進度停滯 | 手動 Run workflow；或等下一個 6 小時 |
| 同步在報表發布前跑 | 只有部分市場的日期 | 基準日門檻擋掉，不會被選成預設 |

### 回補執行紀錄（2026-09-29 ~ 10-05，全程 23 輪）

| run | 結論 | 說明 |
|---|---|---|
| #1、#2 | success | 手動觸發，驗證流程 |
| #3～#5 | cancelled | 腳本跑滿 4.7 小時後被 job 的 300 分鐘上限收掉，**正常** |
| #6 | failure | Parquet 上傳撞到 1,000 asset 上限。回補本身跑完 154.9 分鐘、失敗 0 |
| #7 | success | 當時只剩 2 檔配息要補，12 秒收工——暴露出「不接續下一個資料集」的問題 |
| #8 | failure | 與 #6 同因。修正（一年一檔）是在它開跑之後才推上去的，沒吃到 |
| #9～#23 | success | 連續 15 輪綠燈，2026-10-05 全部補完 |

`cancelled` 與 `failure` 都不代表資料有問題——回補步驟是獨立的一步，
它成功就表示那一輪抓到的資料都已經寫進資料庫了。兩次 failure 都是上傳步驟，
資料零損失。

回補完成後，每 6 小時那一輪會在幾秒內結束（沒有待辦就直接收工），
只有主檔新增股票、或 `REFRESH_DAYS`（預設 30 天）到期時才會真的去抓。

**Parquet 跨輪合併驗證**：回補跨了兩輪，第二輪用 `stock_id` 比對把第一輪的結果
合併回來。抽查 2015／2020／2025 三個年度檔，`(date, stock_id)` **重複 0 筆**，
檔數 1,805 → 2,268 → 2,700 隨年份成長，符合台股上市櫃家數的實際變化。

### 還沒做的防護

- **上游 schema 變動偵測**：現在是靠人看畫面。可以在同步時加不變量檢查
  （例如「資產總計 = 負債總計 + 權益總計」目前 1,976 筆全數相符，
  可以當回歸測試）。
- **資料新鮮度告警**：某張表超過 N 天沒更新時通知。
