財報期別這一列用的是哪一期財報，空白代表該檔沒有財報（ETF、興櫃）

不是每個行業都有這些數字。證交所把財報依行業拆成六檔，其中兩類的上游資料本身有問題（2026-09-29 逐一驗算）：

  • 金控業：「淨收益」對不上利息淨收益＋利息以外淨收益，且 13 家全部「稅前淨利 < 稅後淨利」——會計上不可能。欄位與值錯位，只採用淨利與 EPS。
  • 保險業：旺旺保營業利益 1,931,456 > 營業收入 930,279；中再保營益是營收 6 倍。營收與營業利益不可信，不採用。
  • 銀行業：欄位可信（推算稅前與公告值完全吻合），但銀行沒有單一「營業收入」概念，三個利潤率留空。

所以毛利率只有一般業算得出來，營益率多了證券期貨業，淨利率再多異業。 ROE／ROA／負債比／EPS／每股淨值則是所有行業都有。流動比對金融業不適用（它們的資產負債表沒有流動／非流動之分）。

年度彙總與便宜價 年

來自 FinMind 逐檔日頻在程式內彙總成年度。「近 N 年」一律只算完整年度，不含當年—— 把只過了一半的當年混進平均，下半年配息的公司會被嚴重低估。

便宜價（本益比）財報期 ＋ 近 5 年年化 EPS × 近 5 年最低本益比　獲利角度

篩選欄「股價 ÷ 便宜價」取三者中最寬鬆的當門檻——三種假設本來就不會同時成立，取最嚴的幾乎篩不到東西。

年度彙總目前涵蓋 2015 ~ 2026 年，但只有 4 檔已回補（48 列）。回補完成後為全市場 3,081 檔 × 12 年。

三、三個現在就要知道的限制

① 切到歷史日期時，財報欄位會全部空白。

財報對位是嚴格的 期別 ≤ 基準日，而目前只有 2026-06-30 一期。 切到 2018-01-31 時，毛利率、營益率、ROE、ROA、負債比、流動比、EPS、每股淨值、 以及依賴 EPS 的便宜價（本益比）與便宜價（淨值）全部是空的。

解法：十年季報回補（見第四節第 1 項）。

② 股本有 look-ahead 問題。

股本的對位規則是「優先取 ≤ 基準日，沒有才取之後最接近的」—— 因為公司基本資料的出表日常比交易日晚（2026-09-28 出表對應 2026-09-24 行情）。

但目前只有 2026-09-28 一筆，所以切到 2018 年會顯示 2026 年的股本， 那是當時不可能知道的數字。十年季報回補後會自動解決（資產負債表有歷史股本）。

③ 董監持股永遠只有當期。

交易所那支 API 只給最新一個月，沒有歷史檔。切到 2018 年那四欄會空白—— 這是正確的行為（不會給你未來資料），但也表示歷史回測用不到這幾欄。

四、還沒實作的任務

1. 十年季報回補 最高優先

FinMind TaiwanStockFinancialStatements ＋ TaiwanStockBalanceSheet，每檔 2 次呼叫，實測一次呼叫拿 42 期（2016Q1~2026Q2）。約 11 小時。

解掉 20 個以上的欄位，以及上面的限制 ① 和 ②：

  • 單季數字（毛利率、營益率、淨利率、ROE、ROA 的單季值）＝ 相鄰兩季累計相減
  • 成長率（營收、營業利益、稅後純益的單季與累計）＝ 對比去年同期
  • 年度財報值（2016 毛利率、2016 ROE…）
  • ROE 3 年／5 年／10 年平均
  • 歷史股本（解掉 look-ahead）
  • 近四季 EPS（讓便宜價的本益比法更準確）

2. 現金流量回補

FinMind TaiwanStockCashFlowsStatement，每檔 1 次呼叫，實測 42 期。約 5.5 小時。

解掉 9 個欄位：營業活動現金流量、投資活動現金流量、自由現金流量（單季／累計／年度）。

3. 完成進行中的回補

配息 560 / 3,081（約 4.5 小時）、年度彙總 4 / 3,081（約 11 小時）。每小時 :30 自動跑一輪。

在此之前，5年／10年歷史殖、5年最低PER、便宜價、連續配息年數對大多數股票是空的。

4. Parquet 按年分檔（compaction）

目前 Parquet 是「按股票」分檔，查單檔十年只要開 1 個檔，但查「2018-01-24 全市場」要開 3,081 個檔。

需要第二套按年分檔的佈局，才能支援全市場的歷史掃描。

5. 沒有免費來源，短期不會做

  • EPS（法人估）／最悲觀 EPS（法人估）——券商研究報告，沒有免費 API
  • 單一大股東的持股比例明細——只拿得到職稱為「大股東」者的合計

做法，由簡到繁

方案 A：定期修剪 stock_daily 推薦

保留策略跟現在的取樣一樣——每月最後一個交易日 ＋ 最近 90 天，中間的逐日刪掉。

每季跑一次，容量就穩定在 240 MB 左右不再成長。被刪掉的資料完整保留在 Parquet 裡， 要精確到某一天再去查那邊。

實作成本：一支排程 SQL。不損失任何已經做出來的篩選能力。

方案 B：Parquet 完全分層

資料庫只留最近 3 個月當熱快取，所有歷史都在 Parquet。

容量降到 約 80 MB，但線上要查歷史基準日就得在 Vercel function 裡跑 DuckDB 讀遠端 Parquet——冷啟動要載二進位檔、每次請求要抓十幾 MB，體感會明顯變慢。 而且得先做完第四節第 4 項的按年分檔。

適合「歷史查詢很少用，偶爾在本機查」的情境。

方案 C：換或升級資料庫

  • Neon Launch　約 US$19／月，10 GB — 最省事，但要付錢
  • Turso　免費 5 GB（SQLite 相容）— 免費額度大十倍，但要改 driver 與部分 SQL
  • Supabase　免費 500 MB — 跟現在一樣，換了沒意義

能不能用 Parquet 處理？可以，而且已經在做了。

完整的十年逐日（每檔 2,860 列）都會寫成 Parquet 放 GitHub Release， 實測壓縮後每檔 39–59 KB，全市場約 150 MB，不計入 repo 大小、單檔上限 2 GB。

所以資料庫其實只是「熱快取」——方案 A 刪掉的東西一筆都沒有真的消失。 查法不用下載整包：

SELECT date, close FROM 'https://github.com/cwzstork/stock-data/releases/download/daily-parquet/2330.parquet' WHERE date >= '2020-01-01'

Parquet 每年增加約 15 MB，以 GitHub Release 的額度可以用上百年。
