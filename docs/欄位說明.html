不是每個行業都有這些數字。

  • 金融業完全沒有 EPS——上游的損益表就沒有這一項，不是漏抓。
  • 銀行沒有單一「營業收入」概念，三個利潤率與成長率都會留空。
  • 毛利率只有一般業有；金融業的損益表沒有營業毛利這一項。
  • 金控的「營業收入」是淨收益（利息淨收益＋利息以外淨收益）， 與一般業的營業收入不是同一件事，跨行業比較要有警覺。

月營收與自算預估（4 欄）

來自證交所 t187ap05_L 與櫃買 mopsfin_t187ap05_O（全市場各一次呼叫）， 歷史用 FinMind 逐檔回補。興櫃不強制公告月營收，所以那部分會是空的。

欄位基準說明
月營收年增(2026-08)%單月最新已公布月份 vs 去年同月
營收年增(2026年累計)%年初至今今年累計 vs 去年同期累計
預估EPS(2026年,自算)全年見下方算式
保守預估EPS(2026年,自算)全年同上，保守情境

這是自己算的，不是法人估。法人預估 EPS 沒有免費來源——那是券商研究報告的產出， 各財經網站是向資料商買來的。實測四個常見站台，公開頁面都沒有這個欄位 （CMoney 的 18 種個股頁全掃過，「預估」「EPS」出現 0 次）。

算式：

預估全年營收 = 已公布月份累計 + 剩餘月份（去年同期 × 今年累計成長倍數）
預估 EPS     = 預估全年營收 × 淨利率 ÷ 已發行股數

  基準版　淨利率用近四季
  保守版　剩餘月份假設零成長（直接用去年同期），淨利率取近八季單季最低

全年 12 個月都公布時，剩餘月份為 0，預估值自動收斂成實際值。

實測台積電：累計營收年增 39.26%、近四季淨利率 50.4% → 預估全年 EPS 103.05、保守 78.35（近四季實際 86.28）。

相對法人估，自算有兩個優勢：算式公開可檢驗， 而且月營收有十年歷史所以可回測——這個推估法過去準不準是驗得出來的， 法人估反而拿不到歷史預估值沒辦法驗。

三、現在的限制

① 回補未完成前，大多數股票的進階欄位是空的。

配息已完成（3,081 / 3,081），年度彙總 2,180 / 3,081、季報 6 / 3,081、月營收 3 / 3,081。 在各自補到之前，該檔的單季／累計／成長率／近四季、 5年10年歷史殖、最低本益比、便宜價都會留白。

基準日下拉的每個選項都標出該日檔數（例如 2026-09-24（2,754 檔）、2026-09-23（857 檔））， 差距大是因為歷史日期目前只涵蓋已回補的股票，回補完成後會一起長上來。

② 股本仍有 look-ahead。

畫面上的「股本(2026-09-28)」來自公司基本資料，只有這一期， 切到 2018 年會顯示 2026 年的股本。

季報裡已經有逐季歷史股本（capital_stock）， 但畫面那一欄還沒改接過去——這是待辦第 3 項。

③ 董監持股永遠只有當期。交易所那支 API 只給最新一個月。 切到歷史日期那四欄會空白——這是正確的（不給未來資料），但歷史回測用不到。

④ 部分金控的每股淨值偏高。每股淨值的分母用股本合計，與證交所同口徑 （統一證 29.99、台積電 248.05 完全吻合）。但少數有特別股的金控上游缺股本合計， 只能退回普通股股本，分母偏小（富邦金 90.50 vs 官方 81.22）。 這會連帶影響便宜價（淨值法），金控股看那兩欄要有警覺。

7. backfill_log.synced_at 差 8 小時

欄位是 timestamp without time zone，寫入時把 runner 的本地時間當成 UTC 存進去。

剛寫進去的一列讀回來是 2026-09-29 23:37，而資料庫的 now() 是 2026-09-30 07:37——固定差一個時區偏移。 只影響「最後更新時間」的顯示，不影響任何資料正確性 （進度判斷只看有沒有這一列，不看時間）。改成 timestamptz 即可。

先前的估算太保守，這裡是修正後的數字。

修正一：每列大小。最早用「每列 330 bytes」推算，那是資料量還很少時量到的—— 索引與頁面的固定開銷佔比過高。現在 stock_daily 有 338,313 列， 實測每列 188 bytes，開銷被攤平了。

修正二：漏算了十年月營收。上一版的 120 MB 只加了年度彙總與季報， 沒把 stock_revenue 算進去。那是 3,081 檔 × 141 個月 = 434,421 列， 是第二大的表。補上之後總量從 120 MB 改為 約 190 MB， 爆掉時間從 3 年改為 約 2.6 年。

方案 A：定期修剪 stock_daily 推薦

保留「每月最後一個交易日 ＋ 最近 90 天」，中間逐日刪掉。每季跑一次， 容量穩定在 130 MB 左右不再成長（stock_daily 從 90 MB 降到約 30 MB）。 被刪的資料完整留在 Parquet。

成本：一支排程 SQL。不損失任何篩選能力。

方案 B：Parquet 完全分層

資料庫只留最近 3 個月，容量降到約 100 MB（月營收與季報還是要留）。但線上查歷史基準日要在 Vercel function 裡跑 DuckDB 讀遠端 Parquet——冷啟動載二進位檔、 每次請求抓十幾 MB，體感會明顯變慢，且要先做完待辦第 6 項。

方案 C：換或升級資料庫

  • Neon Launch　約 US$19／月，10 GB — 最省事
  • Turso　免費 5 GB（SQLite 相容）— 要改 driver 與部分 SQL
  • Supabase　免費 500 MB — 跟現在一樣，換了沒意義

Parquet 已經在扛了。完整十年逐日（每檔約 2,860 列）寫成 Parquet 放 GitHub Release， 實測壓縮後每檔 39–59 KB、全市場約 150 MB，不計入 repo 大小、單檔上限 2 GB。

所以資料庫只是「熱快取」，方案 A 刪掉的東西一筆都沒真的消失。查法不用下載整包：

SELECT date, close FROM 'https://github.com/cwzstork/stock-data/releases/download/daily-parquet/2330.parquet' WHERE date >= '2020-01-01'

Parquet 每年增加約 15 MB，以 GitHub Release 的額度可以用上百年。
